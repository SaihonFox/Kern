## 1. Общие принципы
-   **Парадигма:** Expression-oriented (все есть выражение), ООП (множественное наследование), Функциональный стиль.
-   **Типизация:** Строгая статическая с выводом типов. Поддержка Union-типов.
-   **Стиль именования:** `snake_case` для всего (переменные, функции, классы, поля, типы).
-   **Ключевые слова:** `fun`, `type`, `unit`, `use`, `loop`, `match`, `async`, `await`, `op`, `ctor`, `open`, `in`, `is`, `var`.
-   **Блоки кода:** Фигурные скобки `{}` используются В ОСНОВНОМ для многострочных тел. Если тело функции, цикла, условия, конструктора или свойства состоит из одного выражения, фигурные скобки можно отбросить.
-   **Комментарии:**
    -   Однострочные: `// comment`
    -   Многострочные: `/* comment */`
-   **Вызов методов:** ВСЕГДА требует круглых скобок `()`, даже если аргументов нет. Запись `obj.method` без скобок означает передачу ссылки на метод (method reference), а не вызов.
-   **Объявление методов:**
    -   Ключевое слово `fun` **обязательно** используется при объявлении методов внутри классов (`type`, `@type`, `unit`).
    -   Абстрактные методы обозначаются ключевым словом `@fun` и не имеют тела.
-   **Аргументы функций:**
    -   Если функция/метод/function expression не принимает аргументов, круглые скобки `()` в объявлении **НЕ пишутся**.
    -   Если есть хотя бы один аргумент, скобки обязательны.
    -   Символ `_` запрещен в списке аргументов функции.
    -   Поддерживаются **значения по умолчанию**: `fun greet(str name = "Guest")`.
    -   Поддерживаются **именованные аргументы** при вызове: `func(name: "Alex")`.
-   **Ссылка на объект (`$`):**
    -   Внутри методов, конструкторов и расширений типов ссылка на текущий объект обозначается `$`.
    -   Использовать `$` обязательно только при конфликте имен (например, с аргументами) или в расширениях типов для доступа к полям/методам объекта.
    -   В обычных методах класса обращение к полям происходит напрямую по имени, если нет конфликта.
    -   Точка после `$` ЗАПРЕЩЕНА (правильно: `$field`, неправильно: `$.field`).
-   **Игнорирование значений (`_`):** Символ `_` используется как "мусорка" для игнорирования значений при деструктуризации кортежей/коллекций или в циклах. Получить значение из `_` невозможно.
-   **Вывод типа (`var`):** Можно использовать ключевое слово `var` для объявления переменных с автоматическим определением типа.

## 2. Модификаторы доступа и Наследование
-   **Модификаторы доступа:** Указываются перед типом или именем члена.
    -   `pub`: публичный (доступен везде). По умолчанию для классов.
    -   `priv`: приватный (доступен только внутри текущего типа). Сокращение от `private`. По умолчанию для полей и методов.
    -   `prot`: защищенный (доступен внутри типа и его наследников). Сокращение от `protected`.
    -   `int`: внутренний (доступен внутри текущей сборки/модуля). Сокращение от `internal`.
-   **Модификатор `open`:**
    -   Классы и методы по умолчанию закрыты для наследования/переопределения.
    -   Чтобы разрешить наследование от класса или переопределение метода, необходимо явно указать `open`.
    -   Для абстрактных классов (`@type`) и абстрактных методов указывать `open` не обязательно.
-   **Переопределение (`~`):**
    -   Для переопределения метода или поля родителя в классе-наследнике используется `~` перед объявлением.
    -   Если член родителя не `open`, его переопределение через `~` является ошибкой.
-   **Множественное наследование:**
    -   Поддерживается через `type Child[Parent1, Parent2]`.
    -   Родительские конструкторы можно вызывать прямо в списке наследования:
      ```kern
      type A(str name) { }
      type B(str age)[A(age)] { }
      ```
    -   `[A]` является сокращением для `[A()]`.
    -   Аргументы родителя могут быть выражениями на основе параметров конструктора дочернего типа:
      ```kern
      type B(i32 x)[A(x * 2)] { }
      ```
    -   Несколько родителей:
      ```kern
      type C(str name, i32 id)[A(name), B(id)] { }
      ```
    -   Инициализация родителей выполняется до инициализации дочернего типа.
    -   При конфликте одинаковых членов используется явный выбор конкретного родителя. Выбор не является переопределением: дочерний тип только указывает, какой уже существующий член родителя использовать.
    -   Для метода выбор имеет вид `fun $[A]foo(...) -> ReturnType`: он указывает существующий метод `A.foo` как реализацию соответствующего члена дочернего типа. При этом в записи указываются аргументы и возвращаемый тип метода.
    -   Для поля действует тот же механизм выбора родителя: указывается существующее поле конкретного родителя с его типом (включая nullable).
    -   `$[A]member` выбирает только конкретный член `member` из `A`, а не всех членов `A`. Разные конфликтующие члены можно разрешить независимо.
    -   Например:
      ```kern
      type A {
          str name
          fun hello(i32 x) -> str
              f"A: ${x}"
      }

      type B {
          str name
          fun hello(i32 x) -> str
              f"B: ${x}"
      }

      type C()[A, B] {
          fun $[A]hello(i32 x) -> str
          str $[A]name
      }
      ```
      В `C` `hello(i32) -> str` использует существующий `A.hello`, а `name` использует существующее поле `A.name`; новые реализации этих членов не создаются.
    -   `fun A.foo()` зарезервирован для расширений типов и не является синтаксисом выбора родителя.
    -   Конкретный член одного родителя автоматически не считается реализацией абстрактного члена другого родителя. При необходимости это разрешается явно или собственной реализацией в дочернем типе.
    -   `fun $[B]foo()` может явно использовать реализацию `B.foo` для удовлетворения абстрактного `A.foo`; это не является переопределением `B.foo`.
    -   Абстрактные методы существуют только в абстрактных типах. Конкретный `type` должен реализовать все оставшиеся абстрактные методы.
## 3. Типы данных, Литералы и Операторы
-   **Целые:** `i8`, `i16`, `i32`, `i64`, `u8`, `u16`, `u32`, `u64`.
-   **Плавающие:** `f16`, `f32`, `f64`.
-   **Универсальные числовые типы (для ограничений/вывода):**
    -   `inum`: любое целочисленное значение.
    -   `fnum`: любое число с плавающей точкой.
    -   `num`: любое числовое значение (`inum` или `fnum`).
-   **Текст:** `str` (двойные кавычки `"text"`), `char` (одинарные кавычки `'a'`). Не сокращать `char`.
-   **Интерполяция строк:**
    -   Базовая: `f"${expr}text${expr}"`.
    -   Отладка: `f"${expr=}"` выводит `expr=value`.
    -   Форматирование: `f"${val:.2f}"` (float), `f"${val:<10}"` (выравнивание), `f"${val:08d}"` (нули).
-   **Логический:** `bool` (`true`, `false`).
-   **Пустота:** `void`.
-   **Null/None:** `nil` (явное nullable-значение), `none` (специальное значение/тип начального состояния). `none` может использоваться для значения любого типа; `nil` — только для nullable-типа.
-   **Null-safety:**
    -   `T?` допускает `nil`. `nil` допустим только для nullable-типа (`T?`). `none` является специальным значением/типом и может присутствовать у переменной любого типа.
    -   Safe Call: `obj?.prop` и `obj?.method(...)` (вернет `nil`, если `obj` равен `nil`). Работает и для присваивания: `obj?.prop = val` (игнорируется, если `obj` равен `nil`).
    -   Elvis Operator: `val ?: default` (вернет `default`, если `val` равен `nil` или `none`). Тип `default` должен быть совместим с типом значения слева.
    -   Проверка `!= nil` автоматически приводит тип к `T` внутри блока.
-   **Union-типы (Объединения):**
    -   Позволяют переменной хранить значение одного из перечисленных типов.
    -   Объявление: `type alias_name = [Type1, Type2, ...]`.
-   **Коллекции:**
    -   `list<T>`: динамический список.
    -   `array<T>`: фиксированный массив.
    -   `dict<K, V>`: словарь.
    -   **Инициализация:**
        -   С явным типом (список): `<i32>[1, 2, 3]`.
        -   С явным типом (словарь): `<str: i32>["key": 1]`. Двоеточие внутри `<>` указывает на словарь.
        -   Пустые коллекции (тип обязателен): `<i32>[]`, `<str: bool>[]`.
        -   С выводом типа: `[1, 2, 3]` → `list<i32>`, `["k": 1]` → `dict<str, i32>`.
        -   **Запрещено:** `var a = []` (невозможно определить тип и вид коллекции).
        -   **Числовое повышение:** При выводе типа меньшие числовые типы автоматически повышаются к большим в пределах семейства (`i32` → `i64`, `f32` → `f64`). Понижение запрещено. Смешивание `inum` и `fnum` без явного типа — ошибка.
    -   **Массивы:** Сохраняется синтаксис `array<i32>[1, 2, 3]`. Литерал `[...]` без префикса `array` всегда интерпретируется как `list`.
-   **Кортежи (Tuples):**
    -   Группировка значений: `(i32, str)`.
    -   Именованные кортежи: `(i32 x, i32 y)`. Доступ к полям: `tuple.x`.
    -   Литерал: `(10, "hello")`.
    -   Деструктуризация: `(i32 a, str b) = tuple_var`.
    -   Игнорирование: `(i32 a, _, str c) = tuple_var`.
-   **Результат ошибок:** `result<T, E>` (`Ok(val)`, `Err(e)`).
-   **Литералы чисел:**
    -   Десятичные: `123`, `.5` (эквивалент `0.5`).
    -   Суффиксы типов: `5f64` (float 64), `5b` (byte/u8).
    -   Шестнадцатеричные: `0x012DEF`.
    -   Двоичные: `0b01101010`.
    -   Восьмеричные: `0h123523`.
-   **Арифметика:** `+`, `-`, `*`, `/`, `%` (остаток), `**` (степень, как в Python; правоассоциативна, `**=` — составное присваивание).
-   **Повтор (`*` с целым):** `"ab" * 3` → `"ababab"`, `'-' * 20` → строка из 20 дефисов, `3 * "ab"`, `[1, 2] * 2` → `[1, 2, 1, 2]` (`list<T>`). Множитель — любое целое (`inum`/`iN`/`uN`), в обоих порядках операндов; `0` даёт пустую строку/список, отрицательный множитель — `panic`. Это встроенные правила (пользовательское `op i32.*(str)` для этих типов не нужно); `s *= 3` тоже работает.
-   **Сравнение значений:** `==`, `!=`, `<`, `>`, `<=`, `>=`.
-   **Сравнение ссылок:** `===`, `!==`. Эти операторы применимы только к значениям `type` и сравнивают ссылки на объект.
-   **Операторы принадлежности и типа:**
    -   `in`: Проверка вхождения (`5 in [1, 5]`).
    -   `!in`: Отрицание вхождения (`5 !in [1, 5]`).
    -   `is`: Проверка типа (`obj is MyClass`).
    -   `!is`: Отрицание проверки типа (`obj !is MyClass`).

## 4. Переменные и Поля
-   Объявление: `<type> <name> = value` или `var name = value`.
-   Если значение при объявлении не указано, переменная автоматически находится в состоянии `none`.
-   `none` не является признаком nullable-типа: переменная любого типа может находиться в состоянии `none`.
-   `nil` можно присвоить только nullable-переменной.
-   Переменные мутабельны по умолчанию.
-   **Константы** задаются неизменяемым синтаксисом: `i32! limit = 5` / `var! limit = 5` — на верхнем уровне и в локальной области. Ключевого слова `const` нет.
-   **Авто-инициализация в конструкторе:** Если аргумент конструктора имеет то же имя, что и поле класса, и перед ним стоит `$` (например, `ctor(str $name)`), то присваивание происходит автоматически.

### Одноразовое присваивание локальной переменной (`!`)

`!` после типа локальной переменной означает single-assignment: переменная может получить значение только один раз.

```kern
i32! num = 5
num = 10 // ошибка: num уже присвоено значение
```

Можно объявить переменную без начального значения и присвоить её позже:

```kern
i32! num
num = 5
```

До первого присваивания значение такой переменной находится во внутреннем состоянии `none`; читать переменную до первого присваивания нельзя.

Одно присваивание допускается в разных взаимоисключающих ветках, если на каждом фактическом пути выполнения переменная получает значение не более одного раза:

```kern
i32! num

if condition {
    num = 10
} else {
    num = 20
}
```

Повторное присваивание на одном пути выполнения является ошибкой.

`var!` без явного типа и инициализатора не используется. При необходимости одноразовой переменной с выводом типа она сразу инициализируется:

```kern
var! value = 10
```

После инициализации повторное присваивание запрещено.

`!` можно комбинировать с nullable `?` в любом порядке:

```kern
i32!? num = nil
i32?! other = nil
```

После первого присваивания повторное присваивание запрещено независимо от значения.

### `!` у полей

У поля `!` имеет отдельную семантику: это **обязательное поле**, которое должно быть инициализировано при создании объекта.

```kern
type User {
    !str name
}
```

`!` у поля не означает single-assignment после создания объекта.

### Свойства `get`, `set`, `init`

- `get` — чтение свойства.
- `set` — изменение свойства после создания объекта.
- `init` — инициализация свойства во время создания объекта.

`init` не является заменой `!` для полей: `!` обозначает обязательность поля, а `init` определяет способ инициализации свойства.

### `none` и `nil`

- `none` — внутреннее начальное состояние локальной переменной, которая ещё не получила значение.
- `nil` — явно записываемое значение отсутствия для nullable-типа.
- Программист не может явно присвоить `none`.

Пример:

```kern
i32? x

x == none // true
x == nil  // false

x = nil

x == none // false
x == nil  // true
```

Elvis `?:` считает и `none`, и `nil` отсутствующим значением:

```kern
i32? x
x ?: 10
```

Результат — `10`, если `x` находится в состоянии `none` или содержит `nil`.

### Smart casts и flow analysis

- `if x` для nullable-значения означает, что `x` содержит значение.
- `if !x` означает `nil` или `none`.
- `if x == nil` является более узкой проверкой.
- `is` и `!is` участвуют в сужении типа.
- Если условие доказывает наличие значения, внутри соответствующей области `T?` рассматривается как `T`.
- Если после условия flow analysis доказывает наличие значения на всех путях, суженный тип сохраняется после условия.

Пример:

```kern
i32? x

if !x {
    x = 10
}

print(x)
```

После `if` `x` рассматривается как `i32`.

## 6. Функции и Методы
-   Ключевое слово `fun` обязательно везде.
-   Тип аргумента перед именем: `fun name(i32 arg)`.
-   Возвращаемый тип через `-> Type` (опционально).
-   Если функция/метод не принимает аргументов, `()` в объявлении не пишутся.
-   Если есть хотя бы один аргумент, скобки обязательны.
-   **Function Expression:** `fun` может использоваться как выражение для создания значения функции (first-class citizen).
-   Function expression без аргументов имеет вид `fun -> RetType body`.
-   Function expression с аргументами имеет вид `fun(params) -> RetType body`.
-   Function expressions поддерживают замыкания и захватывают мутабельные переменные из внешней области видимости.

### Возвращаемый тип функции

`fun -> i32` в позиции типа означает функцию, которая возвращает `i32`.

Например:

```kern
fun make_counter -> fun -> i32 {
    i32 count = 0

    fun -> i32 {
        count += 1
        count
    }
}
```

Тип `make_counter` здесь:

```text
() -> (() -> i32)
```

То есть `make_counter` возвращает функцию без аргументов, возвращающую `i32`.

### Правила возврата значения

- Если тело функции состоит из одного выражения без `{}`, это выражение автоматически возвращается, а тип может быть выведен.

```kern
fun get_five 5
```

- Если тело заключено в `{}`, по умолчанию возвращается `void`.
- Для возвращаемого значения блока указывается `-> Type`:

```kern
fun get_five -> i32 {
    5
}
```

### Значения по умолчанию

```kern
fun greet(str name = "Guest", i32 age = 18)
```

### Именованные аргументы

```kern
greet(age: 25, name: "Bob")
```

### Лямбды

Последняя лямбда может быть вынесена за скобки вызова.

Тип результата лямбды **всегда пишется явно** после `->`: `fun(i32 n) -> i32 n * n`, `fun -> i32 { … }`. Лямбда без результата: `fun(str s) { … }` (void). Вывод типа результата из тела не делается.

### Тип `never`

`never` — тип выражений, которые не возвращают управление: `panic(…)`, `exit(…)`, `ret`, `stop`, `next` и вызовы функций, объявленных `-> never`. Выражение типа `never` совместимо с любым типом (`if c { x } else { panic("…") }`), блок, оканчивающийся им, не требует значения, код после него считается недостижимым (предупреждение), `if x == nil { panic("…") }` сужает `x` до не-nil. Явно писать `never` в сигнатурах можно: `fun fail(str m) -> never { panic(m) }`.
## 7. Атрибуты
-   Синтаксис: `#[Name]` или `#[Name(arg1, arg2)]` перед объявлением.
-   **Группировка:** Несколько атрибутов можно указывать через запятую внутри одних скобок: `#[Inline, Deprecated("msg")]`.
-   **Дублирование:** Атрибуты одного типа можно дублировать, если сам тип атрибута не помечен специальным системным атрибутом, запрещающим дублирование.

## 8. Классы, Конструкторы и Наследование
-   Обычный класс: `type Name { ... }`.
-   Абстрактный класс: `@type Name[Parents] { ... }`.
-   Наследование указывается в `[]` после объявления типа.
-   Нет родителей -> `[]` не пишется.
-   **Создание объектов:**
    -   `ClassName name(args)`.
    -   `Point p = Point()`.
    -   `Point p()`.
    -   `Point p(10.0, 20.0)`.
-   **Top-level constructor:** `type Name(modifier args)[Parents] { ... }`.
-   Параметры top-level constructor автоматически создают соответствующие поля и их инициализацию.
-   Родительские конструкторы указываются в списке наследования, например `type B(str age)[A(age)]`.
-   `[A]` означает `[A()]`.
-   Абстрактные методы объявляются через `@fun` внутри `@type` и не имеют тела:

```kern
@fun calculate() -> f64
```

-   Абстрактный `@type` может оставлять унаследованные абстрактные методы абстрактными.
-   Конкретный `type` обязан реализовать оставшиеся абстрактные методы.
-   **Свойства:**

```kern
type Example {
    i32 _val

    i32 val {
        get _val
        set(value) _val = value * 2
    }
}
```

-   `get` — чтение, `set` — изменение после создания, `init` — инициализация во время создания.
-   **Статика:** `#type field`, `#fun method`.
-   `#fun` имеет семантику `static`, как в C#.
-   Статический член вызывается через имя типа:

```kern
ClassName.method()
```
## 9. Структуры (`unit`)

`unit` — value type со значениями, копируемыми независимо друг от друга.

### Объявление

```kern
unit Point(f64 x, f64 y)
```

Параметры создают поля `x` и `y`.

Также можно объявлять поля и методы явно:

```kern
unit Point {
    f64 x
    f64 y

    fun length -> f64
        ($x ** 2 + $y ** 2) ** 0.5
}
```

Методы внутри `unit` объявляются через `fun`.

### Создание

```kern
Point p(10.0, 20.0)
```

### Value semantics

Присваивание `unit` создаёт независимую копию значения.

```kern
Point a(10, 20)
Point b = a
```

Изменение `b` не изменяет `a`.

### Сравнение

`==` и `!=` для `unit` сравнивают значения его полей.

### Наследование

`unit` не поддерживает наследование.

### Автоматический `to_str()`

Для `unit` автоматически предоставляется `to_str()`, представляющий значение на основе его полей.

### Деструктуризация

`unit` поддерживает деструктуризацию по своим полям.

### Pattern matching

`unit` может участвовать в `match` как отдельный тип:

```kern
unit Circle(f64 radius)
unit Rect(f64 w, f64 h)

type Shape = [Circle, Rect]

match shape {
    Circle c => 3.14159 * c.radius ** 2
    Rect r => r.w * r.h
}
```

### Вычисляемые свойства

`unit` может иметь свойства, вычисляемые через `get`:

```kern
unit Point(f64 x, f64 y) {
    f64 length {
        get ($x ** 2 + $y ** 2) ** 0.5
    }
}
```

### Операторы

`unit` поддерживает перегрузку операторов через `op`.

```kern
unit Point(i32 x, i32 y) {
    op +(Point other) -> Point {
        Point($x + other.x, $y + other.y)
    }
}
```

### Generics

`unit` может быть generic:

```kern
unit Box<T>(T value)
```

### Immutable unit: `unit!`

`unit!` — неизменяемый value type.

```kern
unit! ImmutablePoint(i32 x, i32 y)
```

После создания состояние `unit!` не может изменяться. Поля `unit!` не могут быть мутабельными.

`unit!` сохраняет value semantics, сравнение по полям, деструктуризацию, pattern matching, вычисляемые свойства, операторы, generics и автоматический `to_str()`.

Отдельного ключевого слова для readonly-структур не вводится: используется именно `unit!`.

### Identity

Отдельная семантика identity для `unit` пока не определена.
## 10. Расширения типов
-   **Методы:** `fun TypeName.method_name(args) -> RetType { ... }`. Внутри `$` обозначает расширяемый объект.
-   **Свойства:** `<ReturnType> TypeName.prop_name body`. Вызываются без скобок. Внутри `$` обозначает расширяемый объект.
-   **Операторы:** `op TypeName.symbol(Args) -> RetType { ... }`.
-   Операторные расширения разрешены для любых поддерживаемых типов, включая примитивы, классы, `unit` и `unit!`.
-   Поддерживаются любые операторы, для которых язык допускает операторную семантику.
-   Внутри операторного расширения `$` обозначает левый операнд.

Пример (для своих типов; повтор `i32 * str` для `str` уже встроен, см. «Арифметика»):

```kern
unit Vec(f64 x, f64 y)

op i32.*(Vec v) -> Vec {
    Vec($ * v.x, $ * v.y)
}
```

После этого `3 * Vec(1.0, 2.0)` даёт `Vec(3.0, 6.0)`.
## 11. Управление потоком
-   Все конструкции управления потоком являются выражениями и возвращают значение.

### Продолжение выражения с новой строки (цепочки)

Строка, начинающаяся с `.`, продолжает предыдущее выражение:

```kern
var evens = numbers
	.filter(fun(i32 n) -> bool n % 2 == 0)
	.map(fun(i32 n) -> i32 n * n)
```

Парсер (а не форматтер) определяет такие продолжения; `?.` в начале строки работает так же.

### Условие `if`

В форме выражения `if condition { ... } else { ... }` заменяет тернарный оператор. Если результат `if` используется как значение, присваивание или возвращаемое значение, ветка `else` обязательна.

```kern
str label = if x > 5 {
    "big"
} else {
    "small"
}
```

Если `if` используется как условие без получения значения, `else` также обязателен по правилу языка, когда конструкция рассматривается как присваиваемое выражение.

### `match`

`match` — основной инструмент pattern matching для значений, Union-типов, типов, guards и условий.

Синтаксис:

```kern
match target {
    pattern => expr
    pattern => expr
    _ => default_expr
}
```

Ветка `_` обязательна, если предыдущие ветки не покрывают все случаи.

`_` — catch-all/discard pattern.

#### Порядок ветвей и предупреждения

Ветки проверяются сверху вниз. Первая совпавшая ветка используется.

Если более поздняя ветка полностью покрыта более ранней, компилятор выдаёт **предупреждение**, но не меняет порядок ветвей и не перемещает их.

Пример:

```kern
match x {
    i32 n => "number"
    5 => "five"       // warning: ветка уже покрыта
    _ => "other"
}
```

Guards также участвуют в анализе покрытия:

```kern
match x {
    i32 n => "number"
    i32 n if n > 10 => "big" // warning
    _ => "other"
}
```

#### Однострочный `match`

Ветки разделяются `;`:

```kern
match x { 1 => "one"; 2 => "two"; _ => "other" }
```

#### Варианты использования

1. Values:
   ```kern
   match code { 200 => "OK"; _ => "Err" }
   ```
2. Types / Union:
   ```kern
   match id { str s => s; i32 n => n.to_str() }
   ```
3. Guards:
   ```kern
   match s { v if v > 90 => "A"; _ => "B" }
   ```
4. Boolean:
   ```kern
   match flag { true => "yes"; false => "no" }
   ```
5. Pure Guards:
   ```kern
   match { x > 0 => "pos"; _ => "neg" }
   ```
6. Охрана через двоеточие и структурные паттерны (раунды 15–16): `i32 n: n >= 500 => "err"`, `Point(x: 0, y: var y) => …`.

### Циклы (`loop`)

-   `loop` всегда возвращает `list` результатов выполнения тела для каждой итерации.
-   Диапазон: `loop var in start..end expr`. Конечное значение `end` не включается.
-   Включительный конец: `loop var in start..=end expr`.
-   Шаг задаётся через `:`: `loop var in start..end:step expr`.
-   Коллекция: `loop var in collection expr`.
-   Игнорирование значения: `loop 0..5 println("hi")`.
-   Пока условие: `loop cond body`; бесконечный: `loop { … }` (выход через `stop`/`ret`); do-while: `loop { … }: cond`. См. «Раунд 7» и «Раунд 15».
-   Тип результата тела должен быть совместимым для всех итераций. Если тело `loop` может вернуть несовместимые типы в разных итерациях, это ошибка компиляции.

Примеры диапазонов:
```kern
loop var i in 1..5 i       // 1, 2, 3, 4
loop var i in 1..=5 i      // 1, 2, 3, 4, 5
loop var i in 1..10:2 i    // 1, 3, 5, 7, 9
```

### Управление циклом

-   `stop` завершает текущий цикл (`break` в C#).
-   `next` пропускает текущую итерацию и переходит к следующей (`continue` в C#).

Пример:

```kern
list<i32> squares = loop i32 i in 1..5 i ** 2
```

Если тело состоит из одного выражения, `{}` можно не писать.

### Деструктуризация коллекций

```kern
(i32 first, list<i32> ..rest, _) = my_list
```
## 12. Перегрузка операторов

Операторы можно перегружать внутри пользовательского типа или как внешнее расширение.

Внутри класса/`unit`/`unit!`:

```kern
op +(OtherType other) -> ResultType {
    ...
}
```

Внешнее расширение:

```kern
op TypeName.+(OtherType other) -> ResultType {
    ...
}
```

Перегрузка разрешена для любых поддерживаемых операторов, в том числе для пользовательских value types (`unit`, `unit!`) и встроенных примитивов. Разрешение перегрузки выполняется по типам операндов по правилам обычной перегрузки функций; правила преобразований и выбора перегрузки соответствуют C#.
## 13. Асинхронность
-   `async fun ... await expr`.
-   Точкой входа программы является функция `main`.
-   `main` может быть без аргументов или принимать один аргумент типа `list<str>` с аргументами командной строки:

```kern
fun main(list<str> args) {
    ...
}
```

-   `main` может быть асинхронной:

```kern
async fun main(list<str> args) {
    await run()
}
```

-   Также допускается `main` без аргументов:

```kern
fun main {
    ...
}
```

-   Асинхронная `main` имеет ту же сигнатуру аргументов, но может использовать `await`.

## 14. Дженерики (Generics)
-   **Передача параметров:** ВСЕГДА используются угловые скобки `<>`, даже при передаче дженерика внутрь другого дженерика.
    -   Пример: `list<map<str, i32>>`.
-   **Ограничения и Наследование внутри объявления:**
    -   При объявлении нового дженерик-типа ограничения указываются ВНУТРИ угловых скобок рядом с параметром через `[...]`.
    -   Синтаксис: `<T[Constraint1, Constraint2]>`. (Разделитель - запятая).
    -   Ограничение конструктора: `ctor(args)`.
-   **Наследование от дженериков:** В отдельных квадратных скобках `[]` после объявления параметров: `type Child<T>[Parent<T>]`.
-   **Множественные параметры:** `<K[IHashable], V[ctor()]>`.

## 15. Разрешение перегрузок (как реализовано в компиляторе)
-   **Идентичность перегрузки:** имя + число generic-параметров + типы параметров. Возвращаемый тип в выборе НЕ участвует.
-   **Применимость** (как в C#): число generic-аргументов (явные `f<A>(..)` должны совпасть по арности, иначе generic-аргументы выводятся);
    позиционные аргументы, затем именованные (позиционный после именованного — ошибка); пропущенные параметры должны иметь значение по умолчанию;
    variadic `..args` принимает список целиком (нормальная форма) либо любое число значений (расширенная форма, пробуется, только если нормальная неприменима);
    ограничения generic-параметров входят в применимость.
-   **Вывод generic-аргументов:** из типов аргументов (и получателя расширения). Параметры лямбды всегда типизированы явно, возвращаемый тип
    лямбды берётся из тела до выбора перегрузки. Несколько нижних границ сводятся к общему типу (`i32`, `i64` → `i64`); конфликт — ошибка.
-   **Лучший кандидат:** по каждому аргументу сравнивается преобразование (identity лучше; затем «целевой тип, неявно приводимый к другому, лучше»;
    знаковый целый лучше беззнакового). Лучший должен быть не хуже по всем аргументам и строго лучше хотя бы по одному. При равенстве:
    не-generic лучше generic, нормальная форма лучше расширенной, меньше значений по умолчанию лучше, более конкретные типы параметров лучше,
    обычный член лучше расширения. Переопределение в потомке скрывает базовую перегрузку.
-   **Неоднозначность** — ошибка `KRN1402` с перечислением кандидатов; неприменимость — `KRN1401` (или более точный код при единственном кандидате).
-   **Числовой литерал без суффикса** (`5`) приводится к любому числовому типу, в который вмещается значение (`u8`, `i64`, `f32`);
    литерал с суффиксом имеет точный тип. (Правило предварительное, ожидает подтверждения заказчика.)
-   **Дерево после привязки:** аргументы вызова расставлены в позиционном порядке, пропущенные — `BoundDefaultArgument`, variadic-хвост упакован в `list<T>`;
    порядок вычисления сохраняется как в исходнике.

## 16. Решения, принятые при реализации (подтверждены заказчиком)
-   **Ошибки:** `try/catch` нет. Ошибки — через `result<T, E>` (`Ok(v)` / `Err(e)`, деструктуризация `Ok(x)`/`Err(e)` в `match`) и `panic`. Ранний выход — `ret` (return).
-   **Числовой литерал без суффикса** приводится как в C# (константное преобразование): `u8 x = 5` — можно, `u8 x = 300` — ошибка. Это правило окончательное.
-   **`a in b`** ≡ оператор `in` на контейнере `b` (`b.op in(a)`); получатель — правый операнд.
-   **Generic-аргументы конструкторов классов выводятся:** `Box(5)` → `Box<i32>`.
-   **Автосвойства:** `i32 val { get; set }`, значение по умолчанию `{ get; set } = 5`; геттер/сеттер/init — отдельные функции.
-   **`typeof<T>()`** (reified, подставляется в рантайме) и `typeof(str name)` (обычная перегрузка) сосуществуют.
-   **Результат `loop`:** если тело выдаёт значение, `loop` возвращает `list<тип тела>`; `stop`/`next` управляют ближайшим циклом.
-   **Байткод/VM:** стековая VM, каждое выражение оставляет на стеке ровно одно значение (void → `Void`); `Call*` всегда кладёт результат.
    Захваченные замыканиями переменные хранятся в ячейках (`KCell`); mutable `unit` копируется (`CopyUnit`) при присваивании и передаче.
-   **Конструкторы:** порядок — инициализаторы родителей, поля (в т.ч. из параметров первичного ctor), `ctor(str $name)`-автоприсваивание, тело.
    Для типов без конструкторов генерируется ctor по умолчанию с теми же инициализаторами.
-   **Цепочка конструкторов (как `: this(...)` в C#):** `ctor(i32 x) : $(x, 0) { ... }` вызывает другой конструктор того же типа (перегрузка выбирается обычным разрешением); тогда инициализаторы полей/родителей не выполняются повторно. Если у типа есть первичный конструктор, каждый вторичный ОБЯЗАН вызывать другой конструктор цепочкой `: $(...)` (как в C#), иначе ошибка `KRN2190`.
-   **Данные в «enum»:** элементы enum не принимают аргументов; перечисление с данными — union из `unit`: `unit! IpAddress(str address)`, `unit! StreetAddress(str city, str street, str house)`, `type Addresses = [IpAddress, StreetAddress]`.
-   **Пользовательская итерация:** `loop var x in obj` вызывает `obj.iter()`, который возвращает `list`/`array`/`dict`. `async loop` работает по `async_iter<T>` с методом `next() -> task<T?>` (`nil` — конец).
-   **Равенство:** `==` для `unit` — структурное по полям; для `type` (класс) — по ссылке, если нет `op ==`.

-   **Степень:** оператор `**` (как в Python), символ для `op` — `**`; `^` освобождён (зарезервирован под побитовое XOR).
-   **`await` как унарный оператор:** `await t1 + await t2` допустим без скобок (`await` — префиксный оператор с приоритетом унарного, выше бинарных).
-   **`list + list`** — конкатенация, результат — новый список (`list<T>`; элементы повышаются к общему типу).
-   **Стандартная библиотека:** `set<T>`, `queue<T>`, `stack<T>` нативные C#-типы (`Kern.Runtime/Collections/Containers`); на Kern остались только протоколы `iter`/`async_iter` (`Kern.Std/std/kern/collections.kern`); `list/dict/array/range/result/str/числа` — нативные (`Kern.Runtime`).
    Нативные «статические» типы (вызов `file.read_text(p)`, `json.to_str(x)`, `env.get(n)`, `random.next(a, b)`, `time.now_ms()`) объявлены через `[KernType("имя")]` + `[KernStatic]`; свободные функции — `[KernModule("модуль")]` + `[KernMember]`.
    Prelude (виден без `use`): `kern.core` (`print`, `println`, `eprintln`, `panic`, `delay`, `exit`), `kern.text`, `kern.collections`, `kern.numerics`, `kern.math`, `kern.io` (`readln`).
-   **Тесты:** функция с `#[test]` попадает в список тестов; `kernc test <путь>`; проверки — `use kern.test[assert, assert_eq, assert_ne, assert_near, assert_nil, assert_not_nil, fail]` (нарушение = panic).
-   **IO-ошибки** (`file.read_text` и т.п.) возвращают `result<T, str>`; `*_async` методы возвращают `task<T>`.
-   **enum:** отдельного синтаксиса нет — перечисление это union из `unit` без полей: `unit Red`, `unit Green`, `type Color = [Red, Green]`; разбор через `match` по типам (`Red _ => ...`).
-   **Интерфейсов нет.** Контракты — абстрактные `@type` с `@fun`; атрибут `#[interface]` на типе — метка для переноса в другие языки. Ограничения generic-параметров — через `T[Тип]` (абстрактный тип, `num`/`inum`/`fnum`), а не `IComparable`.
-   **Видимость по умолчанию:** верхнеуровневые функции, типы и глобалы без модификатора — `pub` (видны из других файлов по `use`); `priv` скрывает в пределах файла. Члены типов по умолчанию `priv`.
-   **Раннего возврата ошибки через `!` нет** (решение заказчика): result разбирается через `match` (`Ok(v) => ...`, `Err(e) => ...`) и `ret Err(...)`. Оператор `!` — только «значение не nil» для `T?`.
-   **`async loop`:** допустим только в async-функции; `async loop var x in stream body` повторно вызывает `await stream.next()`, пока не придёт `nil`. Тип потока определяется по структуре — достаточно метода `next() -> task<T?>` (абстрактный `async_iter<T>` в std — необязательный контракт). Результат цикла — `list<тип тела>`, как у обычного `loop`. Ошибки: `KRN2308` (вне async), `KRN2309` (нет подходящего `next`).

- enum = union из unit; ветки match как в Rust: `Red => …` (имя типа без полей), `StreetAddress(city, street, house) => …` (деструктуризация полей).

### Раунд 4 (решения заказчика)

-   **Обмен значений:** `a, b = b, a` (правые части вычисляются первыми; работает и для `a[i], a[j] = a[j], a[i]`). Парсер раскрывает в блок с временными `$mN`.
-   **Несколько переменных одного типа:** `i32 n1 = 397, n2 = 4, n3`.
-   **Тело без `{}`:** одно выражение допустимо у `if`/`else`/`loop`/`match`-веток: `if ok println("да") else println("нет")`, `loop var i in 1..5 if i % 2 == 0 println(i)`.
-   **Тип возврата по умолчанию — `void`** у функций и методов (вывод типа только у лямбд и операторов). Нужен результат — пишите `-> T`.
-   **Нет `..` в параметрах** (variadic убран): принимайте `list<T>`. `..rest` остаётся только в паттернах деструктуризации.
-   **Короткие имена и свойства:** `len`, `is_empty`, `first`, `last`, `stack.size`, `env.cwd`, `env.os` — свойства, а не функции.
-   **Свойство только для чтения:** `i32 b => a` (тоже что `i32 b { get a }`).
-   **Локальные функции:** `fun name(params) -> R body` внутри тела. Если имя используется раньше объявления — функция поднимается в начало блока (вызов до объявления, взаимная рекурсия); иначе остаётся на месте и видит все ранее объявленные переменные блока. Рекурсия допустима. Без `-> T` — void. Это замыкание типа `fun(P..) -> R`.
-   **Итерация по своим типам:** тип наследует `iter<T>` (`~fun next -> T?`, nil — конец) для `loop`, либо `async_iter<T>` (`~async fun next -> task<T?>`, nil — конец) для `async loop`. Прежний способ `iter() -> list/array/dict` остаётся.
-   **Ленивые импорты:** std-модуль компилируется (и попадает в байткод/память) только если он в prelude либо достижим по `use`; нативные члены разрешаются при первом вызове.
-   **Нативные атрибуты:** `[KernStatic]` работает для методов, свойств и полей (в т.ч. `const`); `[KernStatic, KernProperty(Setter=…)]` на статическом методе даёт статическое свойство; свободные константы/свойства модулей доступны через `use` и `kern.mod.name`.
-   **Сборка (Gradle-подобно; `kern.toml` упразднён в раунде 26 — см. `docs/BUILDER.md`):** `build.kern` — скрипт на Kern с `fun build(workspace w)`; цели `w.target("app") fun (target t) { t.deps = [...]; t.entry = "main"; t.kind = "app"|"lib" }`, свои задачи `w.task(name, after, fun…)`. Встроенные: `цель:compile|run|test|exe|clean`, `build`, `test`, `clean`. Зависимости — исходниками (модули цели + её deps компилируются вместе). Повторная компиляция пропускается по хэшу исходников. Команды `kernc tasks|do|build|run|test|exe|clean`, справка `kernc help [команда]`.
-   **do-while:** принят в раунде 15 как `loop { … }: cond` (см. «Раунд 15»). Циклы `loop cond body` и `loop { … }` — раунд 7.

### Библиотеки (раунд 5, написаны, не проверены компилятором)
-   `loop` заменяет for/foreach/while (решение заказчика); do-while — `loop { … }: cond` (раунд 15).
-   `kern.regex`: `regex r(шаблон[, флаги "imsx"])`, `is_match/find/find_all/replace/split`, `match` (`text/start/end/groups/group`), `regex.try_new`.
-   `kern.csv`: `csv.parse/parse_dicts/to_str`. `kern.yaml`: `yaml.parse/to_str` (подмножество YAML для конфигов). `kern.xml`: `xml.parse/new`, узлы `xml_node` (`name/text/children/attr/child/find_all/add`).
-   `kern.crypto`: sha1/sha256/sha512/md5, hmac_sha256, base64, random_hex, hash_password/verify_password (PBKDF2). `kern.uuid`: `uuid.new()`.
-   `kern.http` (клиент, async): `await http.get(url)` → `result<http_reply, str>`; `post/put/delete/post_json/request`.
-   `kern.web` + `kern.server`: `web_server s(port)`, `s.get("/u/{id}") fun (web_request r) -> web_response …`, `await s.serve()`; обработчики выполняются в потоке VM.
-   `kern.db.sqlite`: `sqlite db(путь)`, `exec/query/scalar/begin/commit/rollback`; `kern.db`: `orm.table<T>(db)` → `table<T>` (`create/insert/update/delete/all/where/find/count`), поле `id` — ключ.

### Раунд 6: потоки, сжатие, оптимизатор, команды (написано, не проверено компилятором)
-   **Потоки (`kern.threading`)** — потоки с общей памятью (с раунда 24, см. ниже): `thread.spawn(f)`, `thread.spawn_with(f, arg[, arg2])` → `worker<R>`; `w.join()` (блокирует) / `await w.wait()` → `result<R, str>` (Err — сообщение паники потока), `w.is_done`. Функция потока может быть замыканием.
-   Общение: `channel<T> ch(ёмкость)` (`send` копирует значение, блокирует при полном ограниченном канале; `recv()` → `T?`, nil после `close()` и опустошения; `try_recv`, `await ch.recv_async()`, `close`, `len`, `is_closed`). Примитивы (передаются по ссылке): `mutex` (`enter/try_enter/exit/run(fun…)`), `atomic` (`value`, `add/increment/decrement/exchange/compare_exchange`), `semaphore(n)` (`wait/try_wait/await wait_async/release`). `thread.sleep(ms)`, `thread.yield()`, `thread.cpu_count()`.
-   **Сжатие (`kern.compress`)**: `compress.gzip/deflate/brotli(str)` → base64-строка; `gunzip/inflate/unbrotli(b64)` → `result<str, str>`; файлы: `gzip_file(путь[, выход])`, `gunzip_file`, `zip_dir`, `unzip`, `zip_list`.
-   **Оптимизатор `-O2`** (peephole по байткоду, после констант-фолдинга `-O1`): снятие пар «чистая загрузка + Pop» (в т.ч. `LdVoid; Pop`), `Not; JmpIf` → `JmpIfNot`, переходы по константе, `Jmp` на следующую инструкцию, прошивка цепочек `Jmp`, удаление недостижимого кода. Инлайнинг и удаление неиспользуемых функций пока не делаются.
-   **Команды:** `kernc dll` — библиотека `.kbc` без точки входа; `kernc fmt [путь…] [--check] [--stdout]` — отступы по скобкам (с раунда 11 — табы + CRLF), чистка пробелов и пустых строк, комментарии сохраняются, код с ошибками не трогается, токены до/после сверяются; `kernc repl` — объявления накапливаются, выражения печатаются, объявления переменных и присваивания повторно выполняются перед каждой строкой.

### Раунд 7: while и бесконечный `loop`, `stop`/`next` внутри выражений
-   **`loop cond body`** — пока `cond` истинно (`bool`; сужение типов в теле работает, как у `if`): `loop n < 3 { n += 1 }`. **`loop { … }`** — бесконечный, выход через `stop`/`ret` (в бесконечном цикле тело — только блок `{}`). Результат — как у `loop var x in …`: `list` значений тела либо `void`.
-   Как отличают от обхода: после `loop` пробуется паттерн + `in`; если `in` не нашлось — это условие. Условие с оператором `in` пишите в скобках: `loop (k in allowed) k += 1`. `async loop` — только обход.
-   **`stop`/`next` в выражениях:** допустимы где угодно внутри тела цикла, в том числе среди недовычисленных операндов (`picked.add(if c { i } else { stop })`). Компилятор запоминает глубину стека в начале итерации (опкод `SaveSp`) и перед переходом восстанавливает её (`RestoreSp`); если в цикле нет `stop`/`next`, `SaveSp` заменяется на `Nop` и вырезается оптимизатором. Старый баг — «мусор» на стеке после `stop` в середине вызова — закрыт.

### Раунд 8: базы данных (SQLite, PostgreSQL, MySQL)
-   Три драйвера с одним интерфейсом: `kern.db.sqlite` (`sqlite db(путь)`, Microsoft.Data.Sqlite 10.0.13), `kern.db.postgres` (`postgres db(url_или_строка)`, Npgsql 10.0.3), `kern.db.mysql` (`mysql db(url_или_строка)`, MySqlConnector 2.6.2). Для сетевых БД есть `postgres.connect(url)` / `mysql.connect(url)` → `result<…, str>` (без паники при недоступном сервере) и конструктор `(host, port, database, user, password)`. URL: `postgres://user:pass@host:5432/db`, `mysql://user:pass@host:3306/db`.
-   Методы: `exec/query/scalar(sql[, args])`, `begin/commit/rollback`, `close`, свойство `last_id`; async: `exec_async`, `query_async` (для сетевых БД не блокируют цикл событий). Параметры — `?` по порядку (для PostgreSQL заменяются на `$1, $2…`). Ошибки SQL — `Err`.
-   `orm.table<T>(db)` работает со всеми тремя: диалект (кавычки, типы колонок, автонумерация `AUTOINCREMENT`/`BIGSERIAL`/`AUTO_INCREMENT`) подбирается автоматически. `insert` возвращает id (явный `id` — как есть, иначе `last_id`).

### Раунд 9: моки (`kern.test`)
-   `mock.create<T>()` создаёт заглушку абстрактного `@type` без ручного класса. Настройка: `mock.returns(m, "метод", значение)` (на любые аргументы), `mock.returns_for(m, "метод", [аргументы], значение)` (приоритетнее; позднее правило перекрывает раннее), `mock.fail(m, "метод", "сообщение")` (метод паникует), `mock.handle(m, "метод", fun (list<object> args) -> i32 тело)` (свой обработчик; тип результата пишется после `->`).
-   Проверки: `mock.calls(m, "метод")`, `mock.calls_with(m, "метод", [аргументы])`, `mock.verify(m, "метод", n)`, `mock.verify_with(m, "метод", [аргументы], n)`, `mock.verify_never`, `mock.reset_calls(m)`. Метод без настройки возвращает значение по умолчанию (не panic); вызовы записываются всегда.
-   Реализация: объект типа T с `KObject.Native = KProxyState`; вызов абстрактного метода без реализации (`CallVirt`) уходит в обработчик прокси. Мок работает только для абстрактных методов (`@fun`). Refit-подобный HTTP-клиент на том же механизме сделан в раунде 10 — шаг (форма API ждёт решения).

### Раунд 10: типизированный HTTP-клиент (два варианта) и атрибуты в байткоде
-   **Вариант A** — `http_client api(base)`: `header(k, v)`, `bearer(token)`, `await api.get<T>(path)`, `delete<T>`, `post<T>/put<T>/patch<T>(path, body)` → `result<T, str>`. Тело запроса — JSON из значения (`str` уходит как есть), ответ разбирается в `T` (`T = str` — без разбора). Статус вне 2xx → `Err("HTTP 404: …")`.
-   **Вариант B** (Refit-подобный) — `http_client.proxy<Api>(base[, заголовки])`: `Api` — абстрактный `@type`, методы помечены `#[get("/users/{id}")]` (`post/put/patch/delete`) и возвращают `task<result<T, str>>`. Параметры с именем из `{…}` подставляются в путь; у GET/DELETE остальные идут в `?query`; у POST/PUT/PATCH первый остальной — JSON-тело. Построено на `KProxyState` (как моки).
-   **Компилятор теперь записывает атрибуты в байткод** (типы и функции; константные аргументы: строки, числа, bool, char, nil) — раньше `Def.Attributes` оставался пустым, и рефлексия атрибутов не работала. Атрибуты `get/post/put/patch/delete` известны компилятору без объявления (нет предупреждения KRN1221).

-   Скрипты `tools/audit_kern_imports.py` и `tools/audit_cs_usings.py` (см. IMPLEMENTATION_GUIDE). Во всех примерах `use kern.*` указывают на существующие модули/типы; ссылки между csproj корректны; найден один пропущенный `using` (исправлен).

### Раунд 11: правки по результатам первой сборки и тестов
-   **Стиль кода:** табы вместо 4 пробелов, CRLF вместо LF (`.editorconfig`, `.gitattributes`). `kernc fmt` теперь по умолчанию выдаёт табы + CRLF (`FormatOptions(UseTabs, NewLine)` в `SourceFormatter`). Продолжения строк (тело ветки на следующей строке, `.цепочка`, операнд после оператора в конце строки) форматтер берёт у парсера (`Parser.ParseForFormatting`), а не угадывает по исходным отступам.
-   **`stop` и `next` имеют тип `never`** (как `ret`): их можно ставить в ветку `?:`/`match` рядом с значением, а после `if x == nil { stop }` переменная `x` считается не-nil.
-   **`next`/`stop` можно использовать как имена методов и полей** (нужно протоколам `iter<T>`/`async_iter<T>`: `~fun next -> T?`).
-   **Smart-cast при присваивании:** `i32? y; if !y { y = 100 }; y + 1` — сужение считается по типу значения до неявного приведения к `T?` (раньше терялось).
-   **`match`:** после ветки `nil =>` последующие привязки (`m => …`) имеют тип без `?`.
-   **Деструктуризация unit/класса по первичному конструктору:** `(f64 x, f64 y) = point`.
-   **Подсказка типа аргументам вызова при нескольких перегрузках:** если подходящие по числу аргументов кандидаты согласны о типе параметра, литералы `[...]`/лямбды получают этот ожидаемый тип (`db.exec(sql, [1, "a"])` → `list<object>`).
-   **Имя модуля:** раньше каждый файл получал имя проекта (все модули «слипались»); теперь имя — из `project a.b:` либо из пути (`geometry/shapes.kern` → `geometry.shapes`, std — `kern.collections` и т. д.).
-   **Нативные generic-члены:** голый `T` в сигнатуре C#-метода больше не считается `T?` (рефлексия nullable считает неаннотированный generic «возможно null»; теперь nullable только при явном `T?`). Свойства-расширения с generic-параметрами метода (`dict.len`, `list.first`) получают подстановку типов получателя.
-   **Лямбда:** после `->` всегда тип результата: `fun (list<object> a) -> i32 42`.
-   **Статические поля/свойства в нативных типах:** `[KernStatic]` работает на методе, свойстве (`[KernStatic] public static int Count { get; set; }`) и поле (`static readonly`/изменяемое); имя можно задать `[KernStatic("name")]`.

### Раунд 12: `=>` в match, формы `loop`, библиотека `kern.time`, `--time`
-   **match:** ветка пишется `pattern [if guard] => body`; старое `->` — ошибка с подсказкой.
-   **loop-переменные:** `loop i32 i in 0..5` и `loop var i in 0..5` объявляют переменную; `loop i in 0..5` без объявления присваивает уже существующей (необъявленное имя — ошибка). Кортежи: `loop (str k, i32 v) in ages`, `loop (var k, var v) in ages`.
-   **Повтор без переменной:** `loop 0..5 body` выполняется 5 раз.
-   **`kern.time`:** `time` (now, utc_now, unix, sleep…), `duration`, `datetime`, `stopwatch`; арифметика `datetime ± duration`, `datetime - datetime`, сравнения. Пример: `examples/18_time`.
-   **Время работы:** `kernc run --time` или `KERN_TIME=1` печатает длительность выполнения программы.
-   **Итерация:** асинхронный протокол переименован `async_stream<T>` → `async_iter<T>` (парный к `iter<T>`).
-   **`<=>`:** для decimal/bigint добавлен `<=>`; `> < >= <=` выражаются через него.
-   **Диагностика:** `KERN_TRACE_MEMBERS=1` печатает поиск членов (для ошибки `нет члена 'len'` у `list<T>`/`dict<T,bool>`).
-   **Правки по первому прогону (раунд 12b):** `T?` неявно приводится к `object` (можно `println(x)` для nullable); операторы `> < + …` работают над параметрами типа с числовым ограничением (`T[num]`); `nil =>` в `match` распознаётся и под приведением к `T?` (значение следующей ветки не nullable); `KERN_TRACE_MEMBERS=1` пишет ещё и в файл `kern-trace.txt` во временной папке (xunit скрывает stderr).

### Раунд 13: GUI `kern.ui` (Avalonia)
-   **Подключение:** `use kern.ui[ui, widget]`. Это внешняя библиотека `libs/Kern.Lib.Ui` (не часть ядра), `[assembly: KernModule("kern.ui", "Kern.Lib.Ui")]`.
-   **Модель:** один тип `widget` для всех элементов (наследование нативных типов появилось в раунде 17, но UI ещё не разделён на `button/label/…`). Вид задаёт фабрика: `ui.label(text)`, `ui.button(text)`, `ui.input(text = "")`, `ui.checkbox(text, is_checked = false)`, `ui.slider(min, max, value)`, `ui.progress(min, max, value)`, `ui.list(items)`, контейнеры `ui.column([...])` / `ui.row([...])`, окно `ui.window(title, w, h, content)`.
-   **Запуск:** `ui.run(window)` блокирует до закрытия окна и возвращает код; вызывать можно один раз за процесс. `ui.every(ms, fun { … })` — таймер интерфейса.
-   **Свойства:** `text`, `value`, `min`, `max`, `is_checked`, `enabled`, `visible`, `width`, `height`, `margin`, `spacing`, `font_size`, `items`, `selected` — читаются и пишутся на элементе; до запуска это модель, после — сразу переносятся на живой контрол. `items` присваивается целиком (изменение копии списка на элемент не влияет).
-   **События:** `on_click(fun {…})`, `on_change(fun {…})` (новое значение читается из свойств), `on_close(fun {…})`. Обработчики выполняются в потоке VM; паника в обработчике печатается в stderr и не закрывает окно.
-   **Дерево:** `w.add(child)` (у окна заменяет содержимое), `w.clear()`, `w.close()`.
-   **Пример:** `examples/19_gui`. Проверяется только компиляция (окно в тестах не открывается).
-   **Не сделано:** декларативный Compose-стиль с `state<T>` и пересборкой; изображения, сетка, диалоги.

### Раунд 14: внешние библиотеки
-   **Что вынесено из ядра:** БД (`kern.db`, `kern.db.sqlite|postgres|mysql`), UI (`kern.ui`) и FFI (`kern.ffi`) — отдельные C#-проекты в `libs/` со своим выводом `libs/_out/<имя>/`. kernc и тесты на них не ссылаются, лишних DLL (Npgsql, Avalonia…) в выводе ядра нет.
-   **Подключение:** kernc сам находит `Kern.Lib.*.dll` в `KERN_LIBS`, `libs` рядом с kernc, `libs/_out` репозитория, `~/.kern/libs`, `libs` проекта и путях `w.lib_path("…")`/`t.lib_path("…")` из `build.kern` (см. `docs/BUILDER.md`). Дальше `use kern.db.sqlite[sqlite]` работает как раньше. Подробно: `docs/LIBRARIES.md`.
-   **Своя C#-библиотека:** сборка `Kern.Lib.<имя>.dll` с `[assembly: KernModule("kern.имя", "Namespace")]` и классами с `[KernType]/[KernMember]/[KernProperty]` — ровно те же атрибуты, что в ядре.
-   **FFI (C/C++):** `use kern.ffi[native_lib]`; `native_lib c("msvcrt")`; `var f = c.fn("strlen", "i64(str)")`; `f.call(["abc"])`. Типы сигнатуры: void bool i8 i16 i32 i64 u8 u16 u32 u64 f32 f64 ptr str; конвенция cdecl. Пример: `examples/20_ffi`.
-   **Пока нет:** Compose-стиль UI. (`.kbc` через `use` — с раунда 25.)

## Раунд 15 — синтаксис

- **Префиксы строк**: `x"\d+"` — значение типа `regex` (≡ `kern.regex.regex("\d+")`, без `use` и без escape); `r"…"` — raw, без escape (`r"""…"""` — многострочная); `v"…"` — verbatim (`""` = кавычка, многострочная). С интерполяцией `${}`: `fx`, `fr`, `fv`. (До раунда 18c префиксы назывались `rx`/`raw`/`frx`/`fraw`.)
- **do-while**: `loop { тело }: условие` (двоеточие может быть на следующей строке). `next` переходит к проверке условия.
- **match**: охрана через двоеточие — `i32 n: n == 200 => "OK"` (вместе с прежним `паттерн if охрана => …`).
- **use для disposable**: `use streamwriter sw = streamwriter("a.txt")` — при выходе из блока (в т.ч. по `ret`/`stop`/`next`) вызывается `dispose()`; не вызывается при панике. Тип должен иметь метод `dispose()`. Добавлены нативные `streamwriter` и `streamreader` (kern.io).
- Отложено: `in/ref/out` (решение пользователя).

## Раунд 16 — события, коллекции, паттерны

- **Структурный match для unit/классов с первичным конструктором:** поля по имени — `Point(x: 0, y: var y) => …`; не названные поля = `_`; `..` допустим (остальные поля). Охрана — после скобок: `User(age: i32 a) : a < 18 => …`. Позиционная форма `Point(x, y)` работает как раньше (смешивать нельзя).
- **События:** native `event<T>` (обработчик `fun(T)`) и `signal` (`fun()`), модуль `kern.events`. `ev += handler`, `ev -= handler`, `ev.emit(arg)`, `ev.len`, `ev.clear()`. Это обычные операторы `+`/`-`, мутирующие событие и возвращающие его же, поэтому новых ключевых слов нет. Обычные делегаты — типы функций `fun(i32) -> i32`; многоадресная подписка у них не поддерживается (используйте `event`).
- **observable<T>:** список с `on_change(fun(str kind, T item))`, kind = add/remove/set/clear; члены: len, is_empty, add, insert, remove, at, set, contains, in, clear, iter, to_list.
- **Единый интерфейс коллекций:** общий протокол обхода — `iter<T>` (`loop` работает для list/array/set/queue/stack/observable); имена `len`, `is_empty`, `add`, `remove`, `contains`/`in`, `clear`, `iter`, `to_list` согласованы у всех. Общий базовый тип — `collection<T>` (раунд 17/17b); `iter<T>` остаётся протоколом на Kern.
- **Атрибуты на свойствах:** `#[Name(args)]` перед свойством/полем/параметром уже разбираются и привязываются к символу (`Symbol.Attributes`); чтение атрибутов в рантайме (рефлексия) — следующий шаг.

## Раунд 17 — наследование нативных типов

- **Правило:** наследование нативных типов берётся из C#: `class KernSet<T> : KernCollection<T>` ⇒ в Kern `set<T>` наследует `collection<T>`. База должна быть публичной и тоже помечена `[KernType]`; её generic-аргументы передаются потомку (`: KernCollection<T>`). Явных атрибутов не нужно.
- **Что даёт:** члены базы видны у потомка; значение потомка неявно приводится к базе (`collection<i32> c = my_set`, параметры функций); `is`/`match` и `Unify` generic-параметров учитывают иерархию; переопределённые в потомке члены скрывают базовые (по сигнатуре). Рантайм-проверка типа — `ClrType.IsInstanceOfType`, поэтому работает без изменений VM.
- **Ограничение (решение пользователя):** Kern-типы НЕ наследуются от нативных (`type MyBtn[button]` нельзя) — только native от native.
- **Реализовано:** `collection<T>` ← set, queue, stack, observable (len, is_empty, contains, `in`, clear, iter, to_list); `stream` ← streamwriter, streamreader (close, dispose). list/array/str/dict/range приводятся к `collection<T>` правилом компилятора — см. раунд 17b.
- Компилятор: `NativeTypeSymbol.Parent/ParentSymbol` (каталог связывает после скана всех сборок), `NativeType.BaseType`, `Conversions.BaseTypes` обходит нативные базы, `MemberLookup` собирает члены баз.
- UI-библиотека пока использует один тип `widget`; разделение на `button/label/…` с общей базой — возможный следующий шаг.

### Раунд 17b — встроенные типы в иерархии

- Корень иерархии коллекций — `collection<T>` (native). Потомки: set, queue, stack, observable (C#-классы) и встроенные **list<T>, array<T>, str (collection<char>), dict<K,V> (collection<(K, V)>), range (collection<i64>)**.
- Для встроенных типов правило подтипирования зашито в компилятор (`NativeType.CollectionParentOf`, корень регистрирует `NativeBinder`); `Conversions.BaseTypes` поэтому видит `collection<T>` у list/array/str/dict/range: передача `[1, 2, 3]` или `"abc"` в параметр `collection<T>`, вывод generic-параметров (`fun f<T>(collection<T> c)`) и `is collection<T>` работают.
- Рантайм: у встроенных значений нет C#-класса, поэтому нативному коду они подаются через адаптер. Атрибут `[KernAdapter(typeof(Фабрика))]` (Kern.Vm.Types) на нативной базе указывает `IValueAdapterFactory`; `Marshaller.ClassOf<T>` вызывает его, если значение не является объектом нужного класса, `TypeChecks.IsInstance` тоже; при возврате в Kern `IValueAdapter.Original` подставляет исходное значение (идентичность list сохраняется). Адаптер коллекций — `KernCollectionAdapter` (len, clear у list/dict, iter; dict обходится парами).
- **`iter<T>` остаётся протоколом на Kern** (абстрактный `@type` с `next`), а не предком коллекций: Kern-типы наследуют `iter<T>` и реализуют `next()`, нативные коллекции `next` не имеют, а Kern-типам наследоваться от нативных нельзя. Обход (`loop`) работает у всех через `iter()` / `next()`.

## Раунд 18 — рефлексия (`kern.reflection`)

Модуль `kern.reflection` (`Kern.Runtime/Reflection`) открывает Kern-коду уже существовавшую C#-рефлексию VM.

- Члены значения `type` (`typeof<T>()`, `typeof(x)`): `name`, `full_name`, `args`, `parents`, `fields`, `properties`, `methods`, `constructors`, `attributes`, `is_enum/is_unit/is_abstract/is_interface/is_declared`, `enum_names()`, `has_attribute(n)`, `attribute(n)`, `get_field/get_property/get_method(n)`, `get_methods(n)`, `get(obj, n)`, `set(obj, n, v)`, `create(args)`, `is_instance(v)`, `is_assignable_from(t)`.
- Обёртки: `field_info`, `property_info` (`get/set`), `method_info` (`call(obj, args)`, `call_static(args)`, `params`, `return_type`), `param_info`, `attribute_info` (`name`, `args`, `named`, `matches(n)`, `instantiate()`).
- Статический `reflect`: `types()`, `find_type`, `types_with_attribute`, `functions()`, `find_function`, `functions_with_attribute`, `module_attributes()`.
- Пример: `examples/24_reflection`. Ничего не компилировалось и не запускалось.
- **Создание типов во время выполнения:** `reflect.define_type("Point3").as_unit().field("x", f64).field_attribute("column").attribute("entity", ["t"]).build()` → значение `type` (класс или unit без родителей/методов). Экземпляр: `t.create([1.0, 2.0, 3.0])` — без конструкторов аргументы идут в поля по порядку. Реализация: `ModuleLoader.AddType` добавляет TypeDef в загруженный модуль (слоты полей 0..n-1), `ModuleIndex.AddType`, `Kern.Vm/Reflection/DynamicTypes.cs`.
- **Рефлексия во время компиляции:** `name_of<T>()`, `field_names<T>()`, `property_names<T>()`, `method_names<T>()`, `parent_names<T>()`, `attribute_names<T>()`, `has_attribute<T>("имя")` вычисляет биндер (`Binder.Meta.cs`), в байткоде остаётся литерал. Только для типов, объявленных в коде Kern; имена зарезервированы. Генерации кода (макросы) пока нет.
- Транспилятор — следующий шаг.

## Раунд 18b — исправления по результатам запуска

- **`нативный член не найден: Kern.Runtime…` при запуске .kbc:** NativeKey ищет члены среди загруженных сборок, а Kern.Runtime при запуске готового .kbc ещё никто не трогал. `Pipeline.CreateVm` теперь грузит её явно.
- **Пути:** в .kbc имена исходников (для трассировки паники) пишутся относительно папки проекта (`src/main.kern`), не абсолютными. `kernc build|dll` по умолчанию кладёт результат в `<проект>/out/<имя>.kbc`, `kernc exe` — в `<проект>/dist/<имя>`, а не в текущую папку (раньше при запуске из bin C#-проекта файлы оказывались там).
- **`x"…"`/`fx"…"`** раскрываются в `kern.regex.regex(…)` — работают без `use kern.regex[regex]`.
- **Внешние библиотеки** (`kern.db*`, `kern.ui`, `kern.ffi`): модуль появляется только после сборки `dotnet build libs/Kern.Libs.slnx` (вывод — `libs/_out`). Ошибка KRN1101 теперь подсказывает это.
- **build.kern:** `use kern.build[workspace, target]` (голый `use kern.build` создаёт алиас `build`, конфликтующий с `fun build`).
- Примеры 14 и 17: добавлен префикс `f` у строк с `${…}`.
- **SQLite: `The type initializer for 'SqliteConnection' threw`:** библиотека грузится из `libs/_out`, а не как зависимость приложения, и нативный `e_sqlite3` не находился. `LibraryLoader` теперь обрабатывает `ResolvingUnmanagedDll` (ищет в `<папка библиотеки>/runtimes/<rid>/native` и рядом с DLL), `KernSqlite` вызывает `SQLitePCL.Batteries_V2.Init()`; в сообщении паники для .NET-исключений теперь видна цепочка внутренних исключений.

## Раунд 18c — префиксы строк

- По решению заказчика: `r` — raw (было `raw`), `x` — regex (было `rx`); `v` и `f` без изменений. Комбинации с интерполяцией переименованы так же: `fr` (было `fraw`), `fx` (было `frx`), `fv`. Старые имена больше не префиксы (`raw"…"` теперь ошибка: идентификатор перед строкой). Изменено в `Lexer.StringPrefixes`, `Parser.IsRegexPrefix`, примере 21.

## Раунд 19 — транспилятор Kern → C# / Kotlin

Библиотека `kern.transpile` (внешняя, `libs/Kern.Lib.Transpile`, собирается через `dotnet build libs/Kern.Libs.slnx`). Работает над типизированным деревом компилятора.

```kern
use kern.transpile

var t = transpiler("csharp")           // или "kotlin"
t.map_script("mappings.kern")          // свои подстановки (необязательно)
match t.file("sample/shapes.kern") {   // result<str, str>: код всех модулей
	Ok(code) => println(code)
	Err(e) => println(e)
}
t.project("sample", "out/cs")          // записать файлы + KernRuntime.cs / KernRuntime.kt
t.text("fun main { println(1) }")      // исходник из строки
```

Скрипт подстановок — обычный Kern-файл; функции необязательны, `nil` = «правила нет»:

```kern
fun map_type(str target, str kern_type, list<str> args) -> str?
fun map_call(str target, str owner, str name, str receiver, list<str> args) -> str?   // owner "" — свободная функция
fun map_member(str target, str owner, str name, str receiver) -> str?                 // чтение нативного свойства
```

Что переносится (этап 1 — ядро языка): функции и extension-функции, `type` (поля, свойства с аксессорами, конструкторы, наследование одного родителя, abstract/open/override), `unit`/`unit!` (`record struct` / `data class`), enum без данных, `match` (значения, диапазоны, типы, кортежи, коллекции с `..rest`, объекты, `Ok/Err`, guard), `loop`/`while`/`stop`/`next`, лямбды, `result` (`KResult` в KernRuntime), `use` → try/finally, generics, async (`async Task` / `suspend`). Имена: C# — PascalCase членов/camelCase локальных, Kotlin — camelCase.

Известные ограничения: см. docs/LIBRARIES.md. Нативные библиотеки (db, ui, ffi) не переносятся.

## Раунд 20 — внедрение зависимостей (kern.di)

Внешняя библиотека `libs/Kern.Lib.Di` (сборка — `dotnet build libs/Kern.Libs.slnx`). Два способа, их можно смешивать:

```kern
use kern.di[container]

var c = container()
c.singleton<logger>(fun { logger("app") })                              // фабрика
c.transient<user_service>(fun(container k) { user_service(k.get<logger>(), k.get<mailer>()) })
c.singleton_as<mailer, console_mailer>()                                // интерфейс → реализация
c.singleton<logger>(fun { logger("audit") }, "audit")                   // именованная

#[singleton] type clock { … }                                           // атрибуты + c.scan()
type report { #[inject] logger log { get; set } }                       // внедрение в свойства
var r = c.create<report>()                                              // конструктор + #[inject]

var s = c.scope()                                                       // область для scoped
s.dispose()                                                             // dispose() у созданных объектов
```

`get<T>()` (panic, если не зарегистрирован), `try_get<T>()` → `T?`, `has<T>()`, `inject(obj)`. Жизненные циклы: `singleton` / `scoped` / `transient`. Подробности — docs/LIBRARIES.md, пример — examples/26_di.

## Раунд 21 — backend-фреймворк (kern.backend)

Внешняя библиотека `libs/Kern.Lib.Backend` (зависит от `Kern.Lib.Di`). Импорт: `use kern.backend[app, ctx, res, chain, middleware, jwt, sse, socket]`, цикл сервера — `use kern.backend.server` (`await a.serve()`).

- **Два стиля, один конвейер.** Функции: `a.get("/x/{id}") fun (ctx c) -> res …`, `post/put/patch/delete/route`, `a.group("/api")` (префикс + свои middleware), `static_files(url, dir)`. Атрибуты: `#[controller("/users")] type …`, методы `#[get("/{id}")]`, `#[post]`, `#[put]`, `#[patch]`, `#[delete]`, плюс `#[auth]` (401 без пользователя) и `#[roles("admin")]` (403). Регистрация: `a.controller<T>()` или `a.scan_controllers()`.
- **Связывание параметров контроллера:** `ctx`/`session` — из запроса; примитивы — из параметров маршрута, затем query (`str?` — nil, если нет); остальные типы — JSON-тело. Результат: `res` как есть; `str` → text; nil → 404 при `T?`, иначе 204; `result` Ok → значение, Err → 400; прочее → JSON.
- **Контроллеры и DI:** `a.services(container)` — на каждый запрос открывается scope, контроллер создаётся с зависимостями и освобождается после ответа (`dispose`). Без контейнера нужен конструктор без аргументов.
- **Middleware:** `a.use(fun(ctx c, chain n) -> res { n.next() })` или готовые `middleware.logger/recover/cors/bearer/basic/jwt_auth/jwt_optional/require_role/sessions/rate_limit`. Порядок: от корня к группе, затем слои маршрута. Если маршрут не найден, всё равно проходят middleware приложения (CORS preflight, логи), ответ 404/405.
- **Auth:** `jwt.sign(user, [roles], secret, ttl)` / `jwt.verify(token, secret)` (HS256); `ctx.user`, `ctx.roles`, `ctx.has_role`; сессии по cookie `kern_sid` (`ctx.session.get/set`).
- **Realtime:** `a.ws("/p") fun (socket s, str text)` (или с open/message/close), `a.sse("/p") fun (sse s)`, `a.ws_broadcast(route, text)`, `a.sse_broadcast(route, event, data)`, `a.stop()`.
- **Потоки.** Kern-код выполняется только в потоке VM: фоновые потоки принимают соединения/сообщения в очередь (`accept`), `handle(work)` исполняет их. Поэтому обработчики не требуют синхронизации.
- **Ограничения:** SSE-ответ не получает заголовки middleware (CORS) — заголовки отправляются при открытии; ws принимает только текстовые сообщения; rate limit и сессии в памяти процесса.
- Пример: `examples/27_backend`. Всё написано без компиляции — ожидаются правки по ошибкам сборки.

## Раунд 22 — макросы (генерация кода при компиляции, `kern.macro`)

Решения пользователя: макрос — Kern-функция над описанием AST; v1 умеет добавлять члены в тип, генерировать новые типы/функции, раскрываться в выражение `имя!(…)` и выдавать диагностики.

- **Определение.** Функции с `#[macro]` (атрибутный макрос) и `#[macro("expr")]` (макрос-выражение), один параметр `macro_ctx m`. Файлы с макросами компилируются отдельным мини-проектом и исполняются в VM до разбора основного проекта. Правило: такой файл использует только std, библиотеки и другие файлы с макросами (не обычные файлы проекта). Сами макро-файлы остаются и в основном проекте как обычный код.
- **Применение.** `#[имя]` или `#[derive(a, b)]` на типе верхнего уровня; `имя!(арг1, арг2)` в выражениях (без пробелов между именем, `!` и `(`; аргументы — исходный текст, разделитель — запятая верхнего уровня).
- **`macro_ctx`.** `target`/`decl` (описание типа: `name`, `kind`, `generics`, `fields` (`name`, `type`, `kind` param/field/property, `default`, `has_default`, `is_public`), `methods`, `attrs` (`name`, `args`, `arg(i)`, `named(k)`, `str(i)`), `parents`, `text`, `has_attr`, `attr`, `has_method`, `field`), `args`, `name`, `file`, `line`; результат: `member(код)` (члены в конец тела типа; тело добавляется, если его нет), `top(код)` (в конец файла), `expr(код)`; вернуть `str` — то же самое (члены для атрибутных, выражение для `expr`); `error`/`warn` — диагностика на месте применения (KRN1502/1503); `quote(s)` — литерал строки; `fresh(prefix)` — уникальное имя.
- **Механика.** Раскрытие текстовое: макрос возвращает исходный код, он вставляется в файл до парсера (`ISourceTransform` в `ProjectLoader`, реализация `Kern.Cli/Macros/MacroEngine`). Вложенные макросы-выражения раскрываются проходами (до 16). Сгенерированный код атрибутными макросами повторно не раскрывается.
- **Ограничения v1:** номера строк в файле с раскрытием сдвигаются (вставки многострочные); цель — только типы верхнего уровня; нет гигиены имён (используйте `m.fresh`); макросы не видят типы/привязку — только синтаксис; LSP/форматтер не раскрывают макросы.
- Пример: `examples/28_macros`. Написано без компиляции.

## Раунд 23 — расширенный async и параллелизм (`kern.tasks`)

Решения пользователя: комбинаторы задач, отмена, параллельные циклы и пул, каналы-потоки и select — всё сразу.

- **Комбинаторы** (`tasks`): `all` (список результатов), `any` (первая успешная), `race` (первая завершившаяся), `settled` (список `result`), `select` (индекс первой готовой — для опроса нескольких источников, в т.ч. `ch.recv_async()`), `timeout(task, ms[, token])` → `result` (`Err("таймаут")`), `delay(ms[, token])`, `run(fun)`, `from_result`, `from_error`, `with_cancel(task, token)`, `retry(fun → task, попытки, пауза_мс)`, `yield_now`.
- **Члены `task<T>`**: `done`, `failed`, `cancelled`, `error`, `cancel()`, `result` (блокирующий).
- **Отмена**: `cancel_token` (источник и токен в одном): `cancel()`, `cancel_after(ms)`, `cancelled`, `check()` (паника «операция отменена»), `delay(ms)`, `wait()`, `on_cancel(fun)`, `child()` (каскад: дочерний отменяется вместе с родителем). Отмена кооперативная: async-функция принимает токен и проверяет его.
- **Параллелизм**: `parallel.map(list, f[, workers])`, `parallel.each(list, f[, workers])` и `pool(n)` с `submit(f[, a[, b]])` / `close()`. С раунда 24 рабочие делят память с программой (замыкания разрешены).
- **Каналы**: `pipe<T>(capacity)` — асинхронный канал внутри одной VM: `send` → `task<bool>` (ждёт места — обратное давление), `recv` → `task<T?>`, `try_recv`, `close`. Для `async loop` — `pipe_stream(p)` из `kern.pipes`. Между потоками по-прежнему `channel<T>`.
- **Механика**: в `Kern.Binding` добавлены обёртки `KTaskRef<T>`/`KTaskNullable<T>` (нативные методы принимают и возвращают `task` без обхода через .NET Task); `TypeMapper` отображает их в `task<T>`/`task<T?>`.
- **Ограничения**: `tasks.run` кооперативна (тот же поток); `pool` не изолирует статику рабочих VM между задачами; pipe не разделяется между потоками; таймер `timeout` держит цикл живым до срабатывания либо завершения задачи. Написано без компиляции; особенно проверьте членов `task<T>` (расширение встроенного типа) и вывод generics в `tasks.all([...])`.
- Пример: `examples/29_async`.

## Раунд 24 — многопоточность с общей памятью (`kern.threading`, `kern.tasks`)
- **Модель**: все потоки видят одни и те же объекты, статические поля и замыкания (никакого глубокого копирования, `ThreadCopy` удалён). Каждый рабочий поток — своя `Interpreter` (`vm.Fork()`: общие Module/Info/типы/статика, свой планировщик и фреймы). Корректность общих данных — на программе, как в C#/Java.
- **Замки**: `mutex` (реентерабельный) и область-защитник — `use var g = m.guard()` держит замок до конца блока (специального ключевого слова `lock` нет: используется существующее `use` с `dispose()`); `m.try_guard(ms)` → `lock_guard?`; `m.run(f)`; `rw_lock` — `use var g = rw.read()` / `rw.write()`; `amutex` — асинхронный замок: `use var g = await am.lock()` можно держать через `await` (не привязан к потоку), `try_lock()`.
- **Примитивы**: `atomic` (i64: `add/increment/decrement/exchange/compare_exchange`), `semaphore`, `channel<T>` (теперь передаёт значения по ссылке), `shared<T>` — общая ячейка (`get/set/swap/update(f)`, свойство `value`).
- **Потокобезопасные коллекции**: `conc_list<T>` (`add/add_if_absent/get/set/update/contains/remove/remove_at/clear/snapshot`, `len`), `conc_dict<K,V>` (`get → V?`, `set`, `has`, `try_add`, `remove`, `get_or_add(k, make)`, `update(k, seed, f)`, `keys()/values()`, `len`), `conc_queue<T>` (`push/pop → T?/peek`, `len`, `is_empty`). `snapshot()`/`keys()`/`values()` возвращают обычный `list` — копию. Обычные `list`/`dict` из нескольких потоков без замка трогать нельзя.
- **Параллельные циклы**: `parallel.map/each` (элементы раздаются динамически), `parallel.for_range(from, to, fun(i32 i))`, `parallel.reduce(list, seed, f[, workers])` (f ассоциативна и коммутативна, seed — нейтральный элемент). Замыкание может менять общее состояние (под замком/atomic/conc_*).
- **async + потоки**: `thread.run(f)` / `thread.run_with(f, a[, b])` → `task<R>` — выполнить в общем пуле потоков (по числу ядер), цикл событий не блокируется; `pool(n).submit(...)`. Задачи (`task`) завершаются только в потоке своей VM: результат рабочего приходит через `Scheduler.EndExternal`, поэтому `await` можно использовать только в потоке, который владеет задачей. `thread.current_id()`.
- **Изменения в рантайме**: `Interpreter.Fork()`; кэш значений enum под `lock(info)`; `Threading/VmExec` (запуск функции на рабочей VM), `Threading/Concurrent.cs`, `SyncApi` переписан; `KernPool` — общий статический пул `Shared`.
- **Ограничения**: `snapshot()/keys()/values()` создают `list` с типом элемента `object` (тип элемента для классовых generics не передаётся); `Monitor`-замок привязан к потоку, в async-коде используйте `amutex`; блокирующий `join()` внутри async-функции останавливает цикл событий; нет защиты от гонок в интерпретаторе для обычных коллекций. Написано без компиляции; проверить: ключ `lock` как имя метода `amutex.lock`, `use var g = await am.lock()`, вывод generics `conc_dict()` без аргументов типа, `T?`-возвраты нативных классов.
- Пример: `examples/30_threads`; тесты `ThreadsShareMemory`, `ConcurrentDictAndParallelReduce`.

## Раунд 25 — библиотеки `.kbc` через `use`
- **Использование** (раунд 26): в `build.kern` потребителя — `t.kbc("../mathx/out/mathx.kbc")` (пути от папки проекта; можно несколько вызовов). Дальше обычные импорты: `use mathx.vec[Vec2, dot]`. Имена модулей — те, что были в библиотеке (путь файла в её `src` либо `project a.b:`).
- **Сборка библиотеки**: `kernc dll <проект>` пишет в .kbc, кроме байткода, **интерфейсные исходники** — копии файлов проекта (после раскрытия макросов), где тела функций, операторов, конструкторов и аксессоров заменены на `panic("kbc")`, а `main` вырезан. Функции без объявленного возвращаемого типа (тип выводится из тела) остаются с телом — иначе сигнатура изменилась бы. Хранятся атрибутами модуля `kern.stub` (`path`, `module`, `text`).
- **Компиляция потребителя**: `KbcStubTransform` (после `MacroEngine`) добавляет интерфейсные файлы к исходникам проекта (пути `<kbc>/<lib>/…`), поэтому типы, перегрузки, generics, `unit`-деструктуризация и проверки типов работают как для обычных модулей.
- **Линковка** (`Kern.Cli/Kbc/KbcLinker`, после `CodeGenerator.Generate`): функции библиотеки сопоставляются с заглушками по ключу (владелец, имя, флаги Static/Getter/Setter/Ctor/Operator/…, типы параметров, число generic-параметров, порядковый номер при совпадении); в заглушку копируется настоящий код, сигнатура, значения по умолчанию; остальные функции (приватные, лямбды, main библиотеки) дописываются в конец. Операнды переписываются по таблице видов операндов опкодов: строки и константы — в пулы потребителя, подписи типов — перенос, функции/типы/глобальные — по картам индексов. Типы сопоставляются по простому имени; раскладка полей проверяется (иначе ошибка «раскладка полей не совпадает»). Глобальные — по имени и типу; статическая инициализация библиотеки выполняется раньше программы.
- **Ограничения**: типы сопоставляются по имени (одноимённый тип в проекте и библиотеке — конфликт); хеш кэша `build`-цели не учитывает .kbc (пересоберите вручную); `dll` проекта, который сам подключает .kbc, включает их код статически; результат функций с выводимым типом хранит тело в интерфейсе; нативные (`kern.*`/libs) зависимости библиотеки должны быть доступны потребителю. Написано без компиляции; проверьте: `panic("kbc")` как тело функции с возвращаемым значением, тела свойств `f64 len => …`, ключи сопоставления для сгенерированных конструкторов и `<static-init>`.
- Пример: `examples/31_kbc` (`kernc dll examples/31_kbc/mathx`, затем `kernc run examples/31_kbc/app`; зависимость объявлена в `app/build.kern`).

## Раунд 26 — решения перед передачей проекта агентам (2026-10-18/19)

Решения заказчика (подробнее и с историей — `docs/DECISIONS.md`):

- **Повтор:** `str * inum`, `char * inum` (→ `str`), `inum * str`, `inum * char`, `list<T> * inum` (→ `list<T>`); отрицательный множитель — `panic`, ноль — пусто. Раздел 3.
- **Константы:** `i32! x = 5` / `var! x = 5` (на верхнем уровне тоже); `const` нет. Раздел 4.
- **`never`:** `panic`, `exit`, `ret`, `stop`, `next` расходящиеся; блок, оканчивающийся `panic(…)`, не требует значения (старая ошибка KRN2104 исчезает). Раздел 6.
- **Лямбды:** тип результата всегда явно: `fun(i32 n) -> i32 n * n`. Раздел 6.
- **Цепочки:** строка, начинающаяся с `.`, продолжает предыдущее выражение. Раздел 11.
- **`kern.toml` удалён.** Проект без `build.kern` работает по соглашению (`src/` + `main.kern`); `kernc run файл.kern` запускает один файл. Всё остальное (цели, зависимости, `.kbc`, внешние библиотеки, настройки компилятора, профили и переменные окружения, подпроекты `include`) описывается в `build.kern` — `docs/BUILDER.md`.
- **Потоки:** только с общей памятью (раунд 24); модель «изолированных VM» (раунд 6) отменена.
- **UI не входит в первый проход**; первый проход = ядро + std + CLI (`docs/ROADMAP.md`). Внешние библиотеки (db, ffi, transpile, di, backend, ui) — второй этап.
- **Команды CLI первого этапа:** `run`, `check`, `test`, `build`, `dis`, `exe`, `dll`, workspace через `build.kern`, `fmt`, `repl`. `kernc test` запускает функции с `#[test]` (добавлено 2026-11-01).
- **Платформы:** Windows, Linux, macOS (CI-шаблон в `.github/workflows/ci.yml`).
- Макросы, рефлексия (рантайм и компиляция), `.kbc` через `use`, async/потоки/`kern.tasks` входят в базовый этап.
- **Индексы и срезы:** `xs[i]`, `s[i]`, `d[k]`; срезы `xs[1..3]`, `s[1..=3]` возвращают новый список/строку; **отрицательный индекс считается с конца** (`xs[-1]` — последний); выход за границы — `panic`.
- **`str.len`** — число UTF-16-единиц (как в C#).
- **`decimal` и `bigint`** — нативные типы std (арифметика, сравнение, `<=>`, преобразования).
- **Байты:** `array<u8>`/`list<u8>`; сжатие, crypto и файловые API принимают/возвращают байты (helpers base64/hex/utf8 остаются).
- **Затенение имён во вложенном блоке разрешено** (предупреждение, не ошибка).
